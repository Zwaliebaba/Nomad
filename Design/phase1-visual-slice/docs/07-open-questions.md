# 07 — Open questions (not blocking phase 1)

1. **Hotkey conflict (resolved, Design D-093: positional QWER/ASDF/ZXCV command card, rotation on Alt+Q/E and mouse 4/5, WASD pan dropped)**: Q/E rotate the camera, but Q is also "Shield surge" on the command card. Phase 1 uses Ctrl+key for command-card hotkeys; the final scheme (for example a grid layout on QWER/ASDF/ZXCV with rotation on mouse buttons 4/5) needs a decision.
2. **Ship altitude vs labels**: the mockup's hostile cruiser label still says "ELEV +26". The phase 1 rule is that all ships fly on z = 16, so the label shows range only. Update the mockup or revisit the rule.
3. **Mockup vs data**: the proposal artboard is the visual source; the voxel data was reconstructed from it. If the artboard changes, re-export the data rather than hand-editing JSON.
4. **Ships are placeholders**: the mockup ships were 2D-baked and could not be exported. Final ship art needs a 3D voxel pipeline (MagicaVoxel `.vox` import is a natural next step).
5. **Rotating minimap**: north-up is chosen; revisit after playtests if players prefer a view-aligned minimap.
6. **Elevation tiers for building placement**: phase 2 must define which tiers a building type may use and how trusses are auto-generated.
7. **Zoom-scale tabs** (System/Sector/Galaxy): visual only in phase 1; their views are a separate design.
8. **True cubes vs z scale 0.8165**: kept behind a config flag; decide after seeing both in motion.
9. **Top bar label (resolved, Design D-022)**: Kestrel-7 is a system. The fixture now reads `SYSTEM KESTREL-7 · OPS GRID 0`; `reference/renders/ops-grid-hud@2x.png` still shows `SECTOR KESTREL-7`. The spec wins (README ground rule 1).
10. **Pylon positions vs sector arcs (resolved, Design D-046)**: the pylons sit at azimuths 225° (N), 315° (E), 45° (S) and 135° (W) around the dome centre. These are exactly the sector *boundaries* in 01 §6, not the centres of the arcs. Resolved: each arc is now centred on its pylon (N 180–270°, E 270–360°, S 0–90°, W 90–180°), with grid north at azimuth 225° (screen-up in view 0). The hostile cruiser at 335° stays in the weak E sector.
11. **"Sector bounds" (resolved, Design D-046)**: the camera clamp in 02 is called "sector bounds", which collides with the Sector layer of the Universe. Renamed to "ops-area bounds" in 02 and `scene_config.json`.
12. **Camera pivot vs screen centre (resolved, Design D-060: keep the formula)**: 02 says rotation pivots around the point on z = 0 at the screen centre, initially the deck centre (-8.5, 9.5, 0). The 01 §1 formula and the reference renders put the deck centre at (970, 492.5), which is 10 px right of and 47.5 px above the centre of 1920×1080. M1 keeps the formula exact: the camera holds the pivot at a fixed screen anchor (the centre plus (10, -47.5) reference pixels, derived from `origin_screen_view0`), and rotates and zooms about that anchor. To pivot about the true screen centre instead, `origin_screen_view0` would become (1050, 537.5) and the reference renders would shift accordingly.
13. **Star count (resolved, Design D-061: about 200, as specified)**: 01 §3 and `scene_config.json` ask for about 200 stars; the mockup behind the reference renders draws 380 (radius 0.5–1.1 px, alpha 0.15–0.6). M1 follows the spec and draws 200.
14. **Ops-grid fade (resolved, Design D-059: match the reference render; exception to ground rule 1)**: 01 §4 and 05 fade each line family from `alpha_near` to `alpha_far` with a smoothstep from 55 voxels around the camera pivot to the screen edge. The mockup instead draws every line at `alpha_far` and stacks near segments on top, in six steps from about 55 to 135 voxels around the origin (0, 0). Near the station the reference therefore shows an effective alpha of about 0.26 (minor) and 0.45 (major) instead of 0.22 and 0.40, and at middle distance (about 100 voxels) its grid is about 1.6× brighter than the spec formula gives. M1 follows the spec; line positions match the reference to within half a pixel. If the grid looks too faint around the station, revisit `alpha_near` or the fade curve.
15. **View names (resolved, Design D-062)**: with grid north at screen-up in view 0 (D-046), view 0 looks north. Views are named by facing direction, N, W, S, E, in the order E cycles them. The fixture's camera-widget label is now `VIEW N · 1/4`.
16. **Shield shape (resolved, Design D-100)**: a dome resting on the ops grid reads as ground-based in space. The shield is now a full globe centred on the ship plane; its equator is the 2D hit circle of Design doc 15 §5.1.
17. **Palette texture instead of a storage buffer (M2)**: doc 05 "Rendering notes" asks for the palette as a storage buffer; its module layout allows "storage buffer/texture". The client creates its GPU device with WebGL2-level limits so that the GLES fallback backend keeps working, and those limits allow no storage buffers. M2 therefore uploads the 339 entries as a 256-texel-wide RGBA8 texture (alpha marks emissive entries) and reads it with `textureLoad` in the vertex shader. Revisit only if the GLES fallback is dropped.
18. **Voxels below the ops-grid plane (M2)**: the `misc` module has 23 voxels at z −4 to −1, in the small prop around (23, 83), so its `bounds.min.z` is −4. Doc 01 §1 puts the deck at z ∈ [0, 1) on the ops-grid plane z = 0, and doc 03 draws elevation cues from `bounds.min.z` down to z = 0. M2 draws the grid under every voxel (doc 05 frame order), so the prop shows over the grid, as it does in the reference render. The M3 cues only concern FA-1 and FB-2, so nothing breaks; either lift the prop in the data or accept props that reach below the plane.
19. **Grid fade in doc 05 (resolved: doc 05 now points to 01 §4 and D-059)**: doc 05 "Rendering notes" still describes the fade as `mix(near, far, smoothstep(r_near, r_far, distance_to_pivot))` with the far radius at the screen edge. Under D-059 the fade is linear between two world radii, tuned to the reference render (01 §4; `near_radius_voxels` and `far_radius_voxels` in `scene_config.json`). The client follows 01 §4; doc 05 should be updated to match.
